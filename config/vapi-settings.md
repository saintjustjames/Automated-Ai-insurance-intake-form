# Vapi Settings (non-prompt)

The prompt only gets you halfway. Delivery does the rest.

## Voice
- Pick a **warmer, natural preset** — not the default.
- Set speed **slightly below default.** Robotic pacing undoes good writing.

## Interruption handling
- **Turn barge-in ON.** Callers need to be able to talk over the AI. This single
  setting does more for "sounds human" than anything in the script.
- **Give endpointing room.** The default "caller stopped talking" threshold is
  tuned for people who answer briskly. Seniors reading a medication bottle out
  loud pause mid-sentence. Too tight and the agent talks over them; too loose and
  every turn feels laggy. Start slightly looser than default and tune on real
  calls — step 12 is where you'll hear it break first.

## Timeouts and limits

Set these explicitly. The defaults are not written for a hold-queue intake.

| Setting | Value | Why |
|---|---|---|
| Silence timeout | Long enough to survive the three-strike silence ladder in the prompt | The prompt handles silence conversationally. If Vapi's own timeout fires first, the caller gets hung up on mid-thought instead of asked "Are you still with me?" |
| Max call duration | ~12–15 min | A full intake runs 4–6 minutes. Anything past 15 is a stuck loop, not a long conversation. Cap it so a wedged call can't bill indefinitely. |
| End call phrases | Leave empty | The agent ends calls by calling `end_intake_call`, not by uttering a magic phrase. A phrase trigger can fire on a caller quoting it back. |

## Greeting: use `firstMessage`, not the model — RECOMMENDED CHANGE

Right now the opening line is generated by the model from step 1 of the prompt.
It should be Vapi's `firstMessage` instead. Three reasons:

1. **Latency.** The first thing a caller hears currently waits on a model round
   trip. A static `firstMessage` starts speaking immediately.
2. **Consistency.** The opening carries the AI disclosure and the trilingual
   offer. That's the one line in the call that should be byte-identical every
   time, not re-improvised per call.
3. **Cost.** No tokens spent generating the same sentence thousands of times.

Time-of-day still works — Vapi supports Liquid templating with `{{now}}`, so the
greeting can branch on the hour without the model's help. Verify the exact
templating syntax against current Vapi docs before pasting.

**When you make this change, also delete step 1's spoken line from the system
prompt** and replace it with a note that the greeting has already been delivered
and the caller's answer to "Sound okay?" is what's being handled. Leaving both in
place makes the agent greet twice.

Not applied yet — it changes live call behavior and needs a Vapi-side change to
land at the same time.

## Structured data extraction — NOT YET WIRED

`flows/intake-schema.json` defines the record one call should produce. It is
currently documentation only; nothing extracts it.

Configure it as the assistant's structured-output schema so Vapi returns the
intake as typed JSON at end-of-call. That JSON is what the n8n workflow in phase
5 consumes — without it, phase 5 starts by re-parsing an English transcript,
which is both lossy and unnecessary.

Two things the schema is deliberately strict about, and the extraction prompt
should repeat:

- **`medications[].verbatim` is always populated; `name` is only filled when the
  caller said it clearly.** Never let the extractor "clean up" a garbled
  medication into a real drug name. That is exactly the hallucination the call
  script spends three rules preventing.
- **`is_proxy` changes who every clinical field is about.** An extractor that
  ignores it produces a medication list attached to the wrong person.

## Success evaluation

Worth turning on once live calls are flowing. Judge a call successful when the
intake reached the summary and transferred, **or** when it correctly short-
circuited (asked for a human and got transferred fast, wrong number, emergency).

A call that completed all fifteen questions on someone who asked for an agent at
question three is a **failed** call, not a complete one. Whatever rubric you
write, make sure it scores that as a failure — otherwise the metric rewards
exactly the behavior the prompt is built to prevent.

## Transcriber (language-critical)
Multilingual detection requires a transcriber that supports it:

| Provider | Setting | Notes |
|---|---|---|
| Deepgram | Nova 2 / Nova 3, language = `Multi` | Best speed/accuracy balance |
| Gladia | Solaria, auto-detect | Strong code-switching |
| Google | latest model, `Multilingual` | Broadest language list, slower |
| Others | single language only | No auto-detection |

**Spanish** is well supported across all of these. **Haitian Creole is much
thinner** — verify before promising it live.

## Tools configured
- `transfer_to_licensed_agent` — the normal ending. **Untested end to end.**
- `end_intake_call` — used only for early exit / declined transfer.

## Transfer configuration

**Mode:** `warm-transfer-experimental` — *not* blind transfer.

Vapi dials the destination and holds the caller with a ringtone. The calls
connect only if someone answers. If voicemail is detected or nobody picks up,
Vapi plays the fallback message and the call ends.

**Destination:** a Twilio ring group that rolls to voicemail.

**Hold audio:** optionally set `holdAudioUrl` to replace the default ringtone.

**fallbackPlan message** — paste this exactly:

> "It looks like every agent is with someone right now. Everything we went over
> is saved for them, and someone will reach out to you shortly. Thanks so much
> for your patience today."

**Known issue:** multiple users have reported warm transfer connecting
immediately instead of honoring the configured mode. Place a real test call and
confirm the hold-then-connect behavior actually happens. Don't trust the setting.

**Hard dependency:** that fallback message promises a human follow-up. Someone
has to actually work the voicemail queue.

## What Vapi cannot do here
Vapi **cannot resume the assistant conversation** after a failed transfer. The
fallback message plays, then the call ends. There is no path back into the
script, so the AI can't collect a preferred callback time at that point. Don't
write a prompt that assumes otherwise.
